## Owner request — training calendar and schedule (2026-10-06, Claude Code)

- **Request:** "A weekly timetable per class: subjects, instructors, rooms or fields, and fitness test and exam dates. Instructors would see their own schedule, and candidates would see 'today and tomorrow' on the portal." Decisions taken without asking: **administrators set the schedules** (`schedule.manage`, both administrator roles); instructors only see (`schedule.view`: their own week plus the classes they teach); an entry happens once or **every week on the weekday of its first date until its last date**, inside the class's academic year; changing a weekly entry changes every week (no single-week cancellation yet — use an announcement); deleting an entry is allowed (a plan, not a record) and audited; candidates see the instructor's name and the room.
- **Code:** migration `2026_10_06_000200_create_schedule_entries_table` (`campus_id` copy for composite FKs class/subject/instructor ↔ campus; CHECKs end > start time and weekly ↔ last date), `ScheduleEntry` (`occurrencesBetween`), `ScheduleEntryPolicy`, `Services\Schedule\{ScheduleScope, ScheduleCalendar, ScheduleService, ScheduleWeek, CandidateSchedule}`, `Staff\ScheduleController` (`/schedule?view=mine|class&class=&period=&campus=&week=`; `/schedule/entries/create|{id}/edit`, store/update/destroy), `Portal\ScheduleController` (`/portal/schedule?week=`), `ScheduleEntryRequest`. The calendar reads examinations (published, on the day they open, local time), fitness tests (staff; portal only with `PORTAL_SHOW_FITNESS`) and attendance sessions (staff with attendance.manage) from their own tables. Audit `schedule_entry.created|updated|deleted`; `ScheduleEntry` is a campus record (morph `schedule_entry`).
- **UI:** sidebar Training Schedule (under Dashboard); week page with My Schedule / By Class tabs, week navigation, items linked when the user may open them (entries → edit for schedule managers, examinations, fitness tests, roll calls); seven columns from 2xl on staff pages, from xl on the portal. - **Code:** migration `2026_10_05_000100_add_two_factor_to_users` (`users.two_factor_secret` encrypted, `two_factor_recovery_codes` encrypted JSON of SHA-256 hashes, `two_factor_confirmed_at`, `two_factor_last_step`), `config/two_factor.php`, `App\Support\Totp` (own ~150 lines instead of a package: HMAC-SHA1, 30 s, 6 digits, Base32, otpauth URI, QR via the existing bacon/bacon-qr-code; checked against the RFC 6238 vectors), `App\Enums\TwoFactorRequirement`, `App\Services\Auth\TwoFactorService` (setup → confirm with a code, recovery codes, disable, reset, `verifyCode` moves `two_factor_last_step` forward atomically so a code works once), `PendingTwoFactorSignIn` (session: user id, 5-minute expiry, wrong-code count).

Limits: 5 wrong codes per account per minute, after 5 wrong codes the password again, route throttle `two-factor-challenge` 30/min per address. - **Staff pages:** account menu → **Two-Step Sign-In** (`/account/two-factor`, `AccountTwoFactorController`, page `staff/account/two-factor.tsx`): Set Up (password) → QR + key → code → recovery codes shown once (Copy, Download); Make New Recovery Codes and Turn Off (password; Turn Off refused while required). Middleware `two-factor` (`EnsureTwoFactorIsEnabled`, after `password.current`) sends required staff to that page (JSON 403). Edit User shows the status and **Reset Two-Step Sign-In** with a reason (`DELETE /users/{user}/two-factor`, `UserTwoFactorController`, same rule as editing, never one's own; audit `user.two_factor_reset`). - **Tablet recovery data** (IndexedDB) is stamped with the candidate and read back only for them, expires after 24 hours, and fully synced records are removed at sign-in and sign-out. Unsynced answers are kept for their owner.

## Authoritative architecture

- Permission-based authorization and Laravel policies. Instructors must hold teaching permissions and an assignment to the relevant offering. Administrators have reporting/monitoring access, not blanket question-editing access.
- `GradeCalculationService` is the only academic grade engine. Finalized assessments contribute; missing scores are not treated as zero. Category weights and passing/warning thresholds remain configurable. Dashboard/report aggregators consume grade engine outputs.
- `MonitoringScope` limits all reports to authorized offerings; filters only narrow the scope. Instructor standing summaries cover taught subjects only.
- `QuestionBankService` owns question mutations; the former incomplete `QuestionService` was removed after checking that no callers remained. `QuestionPresenter::summary` excludes choices/answers; `staff` is authorized staff detail; `forCandidate` is an explicit safe whitelist.
- Publication permanently locks question type/prompt/choices through `QuestionLocking`; inactive questions remain usable by existing published exams but cannot be added/published in new drafts. Topic, default points, explanation and activation remain editable.
- `ExaminationService` owns locked transactional draft edits, question synchronization, publication, result-release changes and archival. IDs/status are explicitly assigned rather than silently discarded by mass-assignment guards. Publication requires a duration and valid active questions. An offering containing examinations cannot be removed.
- Stored exam states: draft/published/archived. Published → Active → Ended is derived from availability dates; this avoids stale scheduled status columns. Once published, delivery settings and questions are fixed. Archive preserves history and requires no in-progress attempts.
- `CandidateAttemptService` serializes starts, saves and terminal transitions. Stable delivery/scoring snapshots preserve question order and scoring rules. Server deadline, revision, attempt limit, access code and navigation rules are authoritative.
- `ExaminationScoringService` uses integer hundredths for point sums. MCQ/true-false are scored automatically; essays hold the result pending. Exam scores contribute to academic grades only through the owner-requested instructor-confirmed posting workflow described above; there is no automatic synchronization.
- `ManualEssayGradingService` checks assignment/grade permission, locks attempts, rejects stale versions, bounds scores and requires reasons for corrections. Every change has an append-only revision; completed scores can now be corrected in the UI. Candidate result release remains configurable.
- Audit logs are append-only at model level; no edit/delete routes. `AuditLogger` recursively removes known secret and answer-content fields. Detailed essay feedback stays in restricted grading history, not general audit values. Exam instruction/code edits record change flags rather than their content.
